# KafkaBoost agent details (moved out of AGENTS.md to keep the always-loaded file small)

Read the section you need. AGENTS.md keeps the one-line version of each rule; these are the full texts, unchanged.

## Rules 11-15 (full text)
11. **Sensors:** the library comes only from the release pinned in `config/sensors.json` (a different SHA-256 means delete and refuse); nothing from it is committed; the user must agree in the app before the download; we never install a driver (CPU temperature/clock/power need the third-party PawnIO driver; without it they are *missing*, never shown as 0); never claim DPC/ISR latency (that is LatencyMon's job); the 80/90 C colors are generic, not chip-specific; any new sensor claim must be something we measured.
12. **HWiNFO on demand (Dashboard card):** proprietary freeware (non-commercial use only): never commit or bundle it. It is downloaded from the official page (https://www.hwinfo.com/download/, the "Portable for Windows 95 and later" zip, address read at run time, no pinned hash) only after the consent box, after the user was shown version, source and signer; the zip must contain `HWiNFO64.exe` and the extracted exe must have a Valid Authenticode signature from REALiX, otherwise delete and refuse. Fetch with `curl.exe` and an honest user agent (Invoke-WebRequest gets a bot-challenge page); never try to solve a challenge: a non-zip reply is `msg.hwinfo.blocked` and the user picks a zip they downloaded. Install only to `%ProgramData%LegionTuninghwinfo<version>` (admin-only ACL). `configHWiNFO64.INI` goes next to the exe before the first start; a user's own INI is never overwritten (turning `SensorsSM=1` on needs `-UpdateIni`, with a timestamped `.bak`). Start only if no HWiNFO64 from that path runs, stop only by `Path`, never with arguments. We could not confirm any session-time limit of the free edition on the official pages, so the app and docs do not state one. **Starting it for the user:** the Dashboard notice (elevated, tiles empty) says in words whether HWiNFO is missing, not running, or running with Shared Memory Support off, and its *Start HWiNFO* button is the same `hwinfo-start` step as the card (no arguments); the checkbox "Turn on Shared Memory Support in HWiNFO's INI (a backup is made)" is the only thing that sends `-UpdateIni`, ticked per start and never remembered. The setting `startHwinfoWithApp` (default off, Settings > Startup) starts an installed HWiNFO once ~15 s after the app starts (also when started hidden at logon), only if it is not running, the app is elevated and its INI **already** has `SensorsSM=1` (`autoStartDecision` in `hwinfologic.js`); it never passes `-UpdateIni`, never edits an INI, and a failure is only logged.
13. **Counter-Strike 2 preset (Optimizations > Counter-Strike 2):** no FPS promise and no anti-cheat claim (we did not test VAC; the page says so). Detection of `cs2.exe` is read-only (Steam registry, `libraryfolders.vdf`, `appmanifest_730.acf`) or a file the user picks, accepted only as a drive path named `cs2.exe` without `.`/`..` parts or wildcard characters (checked in the settings store, `main.js` and `Resolve-Cs2Exe`). The GPU preference is `HKCU\...\DirectX\UserGpuPreferences` with the previous data recorded in the shared state file (section `cs2`) and restored exactly; a preference we did not write is never reverted. The two game files written are `game\csgo\cfg\autoexec.cfg` and the signed-in Steam account's `userdata\<steamid32>\730\local\cfg\cs2_video.txt` (resolution width/height, refresh rate — the user's own choice, never a recommended preset); both fixed names, never through a link, `cs2_video.txt` only edited when it already exists (we never invent one): an existing file gets a timestamped `.bak_` copy first, and restore acts only while the file carries the `// Written by KafkaBoost` marker. `cs2_video.txt` is never fully rewritten — only the specific keys the chosen options touch (`setting.defaultres`, `setting.defaultresheight`, `setting.refreshrate_numerator`/`_denominator`) are changed by a targeted find-or-insert; every other line (shadows, textures, AA, ...) is left byte-for-byte as it was. The signed-in Steam account is found read-only from `HKCU\Software\Valve\Steam\ActiveProcess` (while Steam runs) or the most-recent entry of `config\loginusers.vdf`; no account found means the feature is simply unavailable, never a guess. Only catalog ids from `config/cs2.json` are written (numbers — `fps_max`, resolution, refresh rate — are all range checked); only cvars/keys we are sure exist are in the catalog. Never edit Steam's `localconfig.vdf`: launch options are shown and copied for the user to paste. Disputed or placebo launch options are never ticked by default, and the video options carry no recommended value either — the user decides their own resolution and refresh rate.
14. **Updates and "Apply recommended":** (a) a build that cannot update itself (source clone, portable) gets *Download and install* only when the release has `KafkaBoost-Setup-X.Y.Z.exe`; the page never supplies an address (`app:downloadUpdate` takes none); only `https://github.com/carloskafka/kafkaboost/releases/download/...` and GitHub's release CDN hosts on redirects; 300 MB cap; temp file in `<temp>/KafkaBoost-update` (never Downloads); SHA-256 checked against the release's `SHA256SUMS.txt`; a mismatch deletes the file and a missing checksum file means the installer is NEVER run by the app; the installer starts only after the confirmation dialog, by `spawn(file, [], { shell: false, detached })` from that folder only, and no real installer is ever started in a test. Cleanup removes old `KafkaBoost-Setup-*.exe(.part)` / `SHA256SUMS.txt` from that folder at every start (plain files, never links). The UI says why there is no automatic update and that a clone is updated with `git pull` (no git button); SmartScreen and UAC are never bypassed. The installed build keeps `autoInstallOnAppQuit` off with one *Restart and update* path. (b) The *Apply recommended* confirmation (shared `KB.applyRecommended`) lists, per tweak, what it does, what you may notice, and the exact registry values now / new / after turning off (read-only `tweak-preview` step), admin and restart needs, and the restore-point line; the same detail is shown for advanced and risky tweaks, whose existing confirmations stay. Text is built with `textContent` only.
15. **RAMMap (Optimizations > Memory cleanup (RAMMap)):** Microsoft Sysinternals freeware (Sysinternals Software License Terms): never commit or bundle it. It is downloaded from `zipUrl` in `config/rammap.json` (`https://download.sysinternals.com/files/RAMMap.zip`, no pinned hash because Microsoft updates the file in place) only after the consent box, after the page showed source, signer and licence; `Install-Rammap` refuses an address that does not start with `urlPrefix`, a reply that is not a zip, a zip without `RAMMap64.exe`, and an exe whose Authenticode signature is not Valid with the signer exactly `Microsoft Corporation` (deleted, nothing installed). Installed only to `%ProgramData%\LegionTuning\rammap` (admin-only folder). `Invoke-RammapAction` starts it only from that path, only with `-accepteula` plus the one switch of an action in the config allow-list (`-Ew`, `-Es`, `-Em`, `-Ep`, `-E0`); `main.js` passes `-RammapAction` as an id matching `^[a-z0-9-]{1,40}$`, and PowerShell looks the switch up in the config, so neither the page nor a caller can supply a switch. Never a second copy (refused while a RAMMap64 from that path runs), 120 s limit, a non-zero exit is not logged. RAMMap prints nothing, so every number is ours: `Get-RammapMemory` reads `Win32_PerfRawData_PerfOS_Memory` (locale independent) before and after; a counter that cannot be read is `$null` (shown as a dash), never 0; each successful run appends `{ time, action, switch, before, after, delta }` to `%ProgramData%\LegionTuning\rammap\history.jsonl`. No FPS claim and no claim that it fixes a Counter-Strike 2 memory leak: the page says emptying the standby list can cause stutter. The two "safe" actions (working sets) and three "advanced" ones (modified pages, both standby lists) all ask for a confirmation first. Optional auto clean (setting `autoClean`, off by default, own consent box; `autoCleanThresholdPct` 20-90, `autoCleanCooldownMin` 5-60): only inside a recording play session, only `working-sets`, only above the standby threshold and outside the cooldown, marked `trigger: auto` in `history.jsonl`, state in `auto-state.json`; it switches itself off with one notice if RAMMap is missing, unsigned or not elevated; no FPS or leak-fix claim.

## Roadmap and open items
- **Built since the first version:** Settings + theme + pt-BR, tweak engine and catalog UI, Cleanup, Restore points, the Apps manager, update check with changelog, ThrottleStop on-click download, root launchers.
  **`dynamic-tick-off` tweak** (built): a new `bcdedit` action type in the tweak engine toggling `disabledynamictick` (`Get-BcdElement`/`Set-BcdElement`/`Remove-BcdElement` in `Tuning.ps1`), catalog risk `advanced`, `recommended: false`, `needsReboot: true`. Community sources disagree on its benefit for gaming (steadier timer granularity vs. slightly higher idle power/heat), which is why it is never recommended and carries no FPS claim. **Not verified:** never run for real (the actual `bcdedit` calls are not exercised by Pester, same as the existing `vbs`/`defender`/`dns` action types — only the catalog schema and the preview's `currentOn` field are tested).
  **Memory cleanup (RAMMap)** (built, rule 15): the engine, steps, card/page, demo mode and tests exist. Verified on the real PC: only `rammap-state` (real counters read: 34 GB installed, ~14.8 GB standby, RAMMap reported missing). **Not verified:** the real download, the signature check against the real exe, that the five `-E` switches exist and behave as expected in the current RAMMap version, an elevated run, and whether any of it helps in Counter-Strike 2 (no gain was measured). The live **Memory** side-menu page (Windows only, read-only, 2 s readings while the page is open) is built; **Not verified:** a long session of it on the real PC, and the cost of the 2 s readings while a game runs. Open: any automatic cleaning trigger.
  **Apps manager rules:** commands are always an args array through `src/packages/runner.js` (never a shell string) and every id/query is checked against a strict per-manager regex first (`src/packages/ids.js`); only catalog ids or ids from the manager's own search can be installed; bloatware removal takes only ids from the `bloatware` allow-list of `config/apps.json` (current user only, never `-AllUsers`); import installs only ids that pass the regex and only after the user confirms the shown list; IPC `apps:*` in `main.js`/`preload.js`, UI in `renderer/js/apps.js`. **Not verified:** winget install/uninstall was never run for real, and the macOS (brew) and Linux (flatpak/apt/dnf/pacman, pkexec) code was never run; only command construction and parsing are unit-tested with a fake runner. Native Linux ids (apt/dnf/pacman) are given only where the package is in the distro's main repos; a missing id means "not offered", never a guess.
  **Counter-Strike 2 preset** (built, see rule 13): verified on the real PC only through the read-only detection (the game was found in the second Steam library, the Graphics-settings entry for it exists with `AppStatus=0;AutoHDREnable=2097;` and no `GpuPreference`, no `autoexec.cfg`); the GPU write and the `autoexec.cfg` write were **not** run for real, only against sandboxes, and nothing was checked in game (including whether CS2 runs `autoexec.cfg` by itself and whether `cl_showfps`/`fps_max` behave as described). `cs2_video.txt` tuning (resolution, refresh rate) was added the same way: Steam-account detection and the targeted-key backup/restore logic are unit-tested against sandbox files only, **never** run against a real `cs2_video.txt` or checked in game; the exact root-key name and layout of that file were not independently confirmed, which is why the writer never fully re-parses the file, only finds-or-inserts the specific lines it knows about. **Built since then:** the full rename to KafkaBoost (the repo, package ids and task names keep their historical names on purpose) and the landing site on GitHub Pages (today's docs hub lives in `about-app.html`).
- **Menu names are provisional.** The sections follow the flow the TogsBoost site describes for a typical optimizer (system analysis,
  preparation, optimizations, restore). The reference video could not be analyzed (YouTube blocks automated access), so adjust the
  labels in `app/renderer/index.html` once the exact tab names are known. The old disabled placeholder cards were replaced by the tweak catalog.
- **Presets with a recommendation score** (not built): named tunings per CPU family; each with requirements (CPU generation, hybrid
  or not, VBS, laptop vs desktop), risk and source, scored against the detected system. Only the current profile is validated;
  anything from forums must be labelled unverified. The current ini is the "Default preset" for the 83DE only.
- **Live sensors** (built): the Sensors screen reads CPU/GPU/board/disk/memory sensors with LibreHardwareMonitor 0.9.6 (MPL-2.0, downloaded on demand, see rule 11 and `docs/CONFIGURATION.md`). Verified on the real PC: the download + hash check and a **non-elevated** read (78 sensors: CPU load, GPU, memory). **Not verified:** an elevated read (disk/board/fan sensors), any CPU temperature (PawnIO is not installed there), anti-cheat behaviour with that driver, and a long session (the library is reopened by a new PowerShell for every read, about 1 s each).
- **HWiNFO on demand** (built, Dashboard card): see rule 12 and `docs/CONFIGURATION.md`. Verified on the real PC: reading the official page, the portable zip download into a scratch folder (via `curl.exe`) and the Authenticode check (Valid, REALiX, version 8.54). **Not verified:** the elevated install under `%ProgramData%`, starting and stopping HWiNFO from the app, the first-start dialog of HWiNFO with the template INI, and a protection page from the site (Invoke-WebRequest was served one; `curl.exe` was not).
- **Insights** (built, Windows only; sensor source: HWiNFO shared memory): the **play session recorder** logs temperature, P/E clocks, package power and standby / free memory (`Get-RammapMemory`, read-only; a counter Windows does not report is null, never 0; the memory part is not gated by HWiNFO) every 5 s while the user plays (a manual button, or automatic when Settings > "Record play sessions automatically" is on: it checks every 10 min, starts at >= 40 W package power and stops after 30 s below 25 W). The summary gives duration, the lowest and highest standby and free memory (rows only when the session recorded them), peak and average, the share of readings at PL1/PL2 and the WHEA count since start; throttle flags are not readable, and the summary says so. The last 20 sessions are kept. The **boost clock advice** is advisory only and never applies a change: it needs >= 3 loaded sessions (>= 5 min, average power >= 40 W) and answers raise (+1 ratio step only if peak <= 85 C, the clock reached the cap, under PL1, no WHEA), hold (WHEA, hot >= 90 C, marginal 86-89 C, not cap-bound, power-bound) or lowerCheck (WHEA 19 -> -80/-80/-70 mV, rule 1), or notEnough. **Not built:** a guided before/after comparison, a per-CPU-family recommendation score, and CS2 detection (automatic detection of `cs2.exe` is not built).
- Not tested on a fresh Windows install; `npm run dist` builds locally (unsigned) but `release.yml` and the Linux/macOS CI legs have never run on GitHub; the macOS/Linux code (launchers, autostart) was never run.
- FPS was never measured, only judged by feel.
- **Landing site** (built and published: the GitHub Pages deploy succeeded): `docs/index.html` + pages in EN and `pt-br/`; every number on it comes from `config/tweaks.json`, `docs/TESTING.md` or `docs/RESULTS.md` (checker enforces the first two). No FPS claims, testimonials or user counts. The repository is MIT licensed (`LICENSE`), so the site says "open source (MIT licence)"; the checker fails if a page says so while `LICENSE` is missing. ThrottleStop, HWiNFO and LibreHardwareMonitor are not covered by it and keep their own licences.
- **Still not built or never run:** the guided before/after test session, presets per CPU family, a tested release/installer on a fresh Windows install, and any Linux or macOS run (launchers, autostart, Apps providers).
